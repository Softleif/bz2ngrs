# 04 — Rust ecosystem: baseline and building blocks

Scope: what a Rust port of bz2-ng (`/Users/pascal/code/tfenne/bz2-ng`) would compete against inside seqair, and which existing crates/intrinsics it can be built from. Local sources are under `~/.cargo/registry/src/index.crates.io-*/`; crates not in the local registry were downloaded into the session scratchpad and read there. Toolchain used for probes: rustc 1.96.0 (seqair pins 1.98.1 in `rust-toolchain.toml`).

## 1. The baseline: `bzip2` 0.6.1 → `libbz2-rs-sys` 0.2.5

**Backend selection.** `bzip2-0.6.1/Cargo.toml`: `default = ["dep:libbz2-rs-sys"]`, with `libbz2-rs-sys` pulled in with `default-features = false, features = ["rust-allocator"]`. The C backend is opt-in via the `bzip2-sys` feature (`bzip2-0.6.1/src/lib.rs:58-61`: `#[cfg(feature = "bzip2-sys")] extern crate bzip2_sys as ffi; #[cfg(not(...))] extern crate libbz2_rs_sys as ffi;`). seqair depends on `bzip2 = "0.6.1"` with default features (`crates/seqair/Cargo.toml:38`), and `Cargo.lock` has `libbz2-rs-sys 0.2.5`, so **seqair currently runs the pure-Rust libbz2-rs-sys**, not C libbz2. (`bzip2-sys 0.1.13+1.0.8` is present in the lockfile only via rust-htslib, a dev-dependency used as test oracle — handy for differential tests against real C libbz2.)

**How faithful.** libbz2-rs-sys (Trifecta Tech Foundation, `github.com/trifectatechfoundation/libbzip2-rs`) is a c2rust translation of libbzip2 1.0.8 that was then cleaned up into mostly-safe Rust; it keeps the same algorithms and structure: `blocksort.rs` has `fallbackSimpleSort`, `fallbackQSort3`, `fallbackSort`, `mainGtU`, `mainSimpleSort`, `mainQSort3`, `mainSort`, `BZ2_blockSortHelp`; `compress.rs` has `generate_mtf_values`/`send_mtf_values`/`compress_block`; CRC is the byte-at-a-time 256-entry table (`crctable.rs`, `bzlib.rs:872` `crc = (crc << 8) ^ BZ2_CRC32TABLE[...]`); the decoder is libbz2's state machine with the one-pointer-at-a-time inverse BWT. Total ~7.3 kLoC; `unsafe` is concentrated in `bzlib.rs` (78 occurrences, the C ABI layer) with ~1 each in blocksort/compress/decompress. Output should be byte-identical to C libbz2 (same sorter, same Huffman code). No SIMD, no prefetch, no slice-by-N CRC.

**Published performance vs C libbz2** (Trifecta blog "bzip2 crate switches from C to 100% rust", 2025-06-17, https://trifectatech.org/blog/bzip2-crate-switches-from-c-to-rust/; CPU cycles, unnamed machine): compression −14.9% (sample3.ref, level 1), −14.3% (silesia-small.tar, level 1), −9.7% (silesia-small.tar, level 9); decompression −4.5% to −10.0% across six files. The post says Rust "generally outperforms" C and is never substantially slower; a third party (Anisse, via a fediverse post) disputed the decompression claim ("it depends"). I found no independent benchmark.

**Implication for the target.** Treat libbz2-rs-sys as ≈ C libbz2, at most ~10–15% faster. bz2-ng's claimed 2.7–10× (compress) and 1.6–4.9× (decompress) over C libbz2 therefore translate to roughly 2.4–9× and 1.5–4.5× over what seqair runs today. `notes/05-baseline-bench.md` should be the authority for measured numbers on this machine.

Side note: seqair's `Cargo.toml` sets `[profile.dev.package] bzip2.opt-level = 3`, but the codec lives in `libbz2-rs-sys`, which is not listed, so dev/test builds probably run the codec unoptimised (only the thin wrapper gets O3). Cheap to fix independently of any port.

## 2. `fearless_simd` 1.1.0 (+ `fearless_simd_macros` 0.1.0)

Already a seqair dependency (`crates/seqair/Cargo.toml:41-42`), and seqair's dev-deps enable `force_support_fallback` so tests can run every level including scalar (`crates/seqair/src/simd_levels.rs`). That maps directly onto bz2-ng's `BZ2NG_TIER` test forcing.

**Model.** Token types `Fallback`, `Sse2`, `Sse4_2` (x86-64-v2: sse4.2+popcnt+cmpxchg16b), `Avx2` (x86-64-v3: avx2, bmi1/2, lzcnt, fma, movbe, f16c), `Avx512` (Ice-Lake class), `Neon`, `WasmSimd128`. `Level::new()` does runtime detection on x86 only (cached in a `LazyLock`); **on aarch64 it returns the static baseline (`Neon`) with no runtime detection** (`fearless_simd-1.1.0/src/lib.rs`, `Level::new`). Functions are written generic over `S: Simd`, annotated `#[simd]` (proc macro, makes the body inherit the token's target features) and called via `dispatch!(level, simd => f(simd, ...))`, which monomorphises once per level and matches on the `Level` enum (call it per block/chunk, not per byte). `kernel!` (`src/kernel_macros.rs`) wraps a safe fn whose first param is a concrete token (`Neon`, `Sse4_2`, `Avx2`, ...) in an inner `#[target_feature]` fn, so `core::arch` intrinsics can be called safely inside; vectors convert to/from raw `__m128i`/`uint8x16_t` with `.into()` / `.simd_into(token)`. Limitation: the macro's target-feature set is fixed per token — you cannot add `pclmulqdq`, `aes`/PMULL, `crc` or `sha3` through it. `force_support_fallback`: keeps the `Level::Fallback` variant compiled on targets whose baseline is better (aarch64, x86-64), so a scalar path can be selected/tested. Feature flag `std` (default) is needed for `Level::new()`.

**Types and ops (per `src/generated/simd_trait.rs`).** All widths 128/256/512 for u8/i8/u16/i16/u32/i32/u64/i64/f32/f64 (u8x16, u8x32, u8x64, u16x8, u32x4, ...), plus `maskNxM`. Wider-than-native types are emulated as pairs/quads (e.g. u8x32 on NEON and SSE4.2 is two u8x16). Relevant ops on u8x16: `splat`, `from_slice`/`store_slice` (slice length must equal 16, else panic; `load_array_ref`/`store_array` for `&[u8;16]`), `as_slice()` for lane access, `simd_eq/ne/lt/le/gt/ge` → mask, `and/or/xor/not`, `min/max`, `select(mask, a, b)` (SSE4.x/AVX2: `pblendvb`; NEON: `vbslq`), `slide::<N>(a, b)` (= `palignr`/`vext`), `swizzle_dyn` (SSE4.2/AVX2: `pshufb`; NEON: `vqtbl1q`; **Sse2 and Fallback: scalar loop**), `swizzle_dyn_precise`, `concat_swizzle_dyn`, `zip_low/zip_high` (unpacklo/hi, vzip1/2; on AVX2 the u8x32 version adds a cross-lane `vperm2i128` to be order-correct), `unzip`, `widen`/`narrow`, `reduce_min/max/sum`, `count_ones`, `compress`/`expand`, `bitcast` (reinterpret u8x16↔u16x8 etc.), `combine`/`split` (128↔256). Masks: `to_bitmask()` → u64, `from_bitmask`, `any_true/all_true/...`. There is no "first set lane" op; use `to_bitmask().trailing_zeros()`.

**to_bitmask cost.** SSE4.2/AVX2 → a single `pmovmskb` (1 bit/lane, like bz2-ng). NEON `to_bitmask_mask8x16` is `vand` with weights + `vext` + `vzip1` + `vaddvq_u16` (4 ops, 1 bit/lane); bz2-ng instead uses the 1-instruction `vshrn_n_u16(...,4)` nibble mask (4 bits/lane, `ctz >> 2` for the first lane, `vec.h:VEC_MB`). For the hot NEON paths, write a `kernel!(fn ...(neon: Neon, ...))` using `vshrn_n_u16` directly. NEON `to_bitmask_mask8x64` uses a uzp/sri tree, comparable to bz2-ng's `vpaddq_u8` reduction in `change_mask64`.

**Map of bz2-ng vector ops → fearless_simd** (`c/lib/vec.h`, `c/lib/kern_template.h`):

| bz2-ng op (x86 / NEON) | used for | fearless_simd |
|---|---|---|
| `vec_ld`/`vec_st` (`loadu`/`vld1q`) | everywhere | yes: `u8x16::from_slice`/`store_slice` (bounds-checked slices; may need `load_array_ref` on `&[u8;16]` via `try_into` to keep checks out of loops) |
| `vec_dup` (`set1`/`vdupq`) | | yes: `splat` |
| `vec_eq` (`pcmpeqb`/`vceqq`) | | yes: `simd_eq` |
| `vec_and` | | yes (`&` on vectors and masks) |
| `vec_mask` (`pmovmskb` / `vshrn` nibble mask) | first-change / run detection | yes via `to_bitmask` (x86 optimal; NEON 4 ops vs 1 — use `kernel!` + `vshrn_n_u16` for the hot path) |
| `vec_shift1` (`palignr 15` / `vextq 15`) | MTF/run scans | yes: `slide::<15>(prev, cur)` |
| `vec_sel_upto` (`pcmpgtb`+`pblendvb` / `vcleq`+`vbslq`) | decoder MTF head update | yes: `simd_le(iota, splat(k))` + `select` |
| `vec_lane0`/`vec_lane15` (`movd`/`pextrw`, `vgetq_lane`) | | yes: `as_slice()[0]` / `[15]` (check codegen) |
| `vec_bcast_lane` (`pshufb` with splat k / `vqtbl1q`) | decoder MTF lookup | yes: `swizzle_dyn(splat(k))` on Sse4_2/Avx2/Neon; scalar on Sse2/Fallback (fine: bz2-ng's x86 vector baseline is SSE4.1 too) |
| AVX2 `_mm256_cmpeq_epi8`×3 + `and` + `movemask` (`run4_mask`, `run_length`) | RLE1 input stage | yes: u8x32 `simd_eq`, `&`, `to_bitmask` |
| `vtstq_u16` / `_mm_and_si128`+`_mm_min_epi16` (`put_zero_run`) | zero-run digits | yes: u16x8 `&`, `min` (or `simd_ne` + `select`) |
| `vpaddq_u8` tree (`change_mask64`, NEON) | 64-lane change mask | yes: mask8x64 `to_bitmask` (different but similar-cost sequence) |
| `unpacklo/hi_epi8` / `vzip1q/2q_u8` + `min_epu16`/`vminq_u16` | least-rotation 2-byte window min | yes: `zip_low/high` + `bitcast` to u16x8 + `min` (AVX2 u8x32 zip adds a permute bz2-ng doesn't need — order is irrelevant for a min; use `kernel!` or u8x16 if it matters) |
| `_mm_minpos_epu16` / `vminvq_u16` | horizontal min | yes: `reduce_min` (NEON = `vminvq`; x86 = 3 shift+min steps instead of `phminposuw`, negligible, outside loop) |
| `_mm256_extracti128`/`castsi256` | | yes: `split()` |
| `ctz`/`clz`/`popcount`/`bswap` | | std: `trailing_zeros`, `leading_zeros`, `count_ones`, `swap_bytes`/`from_be_bytes` |
| `__builtin_prefetch` / `_mm_prefetch` | inverse BWT walk (`dec_block.c:502`), others | **missing** → `core::arch` (see §4) |
| PCLMULQDQ / VPCLMULQDQ / PMULL / ARMv8 CRC32 | CRC | **missing** (and not detected by `Level` except as part of `Avx512`) → own `#[target_feature]` fns + `is_x86_feature_detected!` / `is_aarch64_feature_detected!` (see §3) |

Net: every vector op in bz2-ng's kernels has a fearless_simd equivalent; only the NEON mask extraction is materially less efficient through the portable API and should go through `kernel!`. Prefetch and carry-less multiply / CRC instructions are outside fearless_simd and need plain `core::arch` with separate feature detection (on aarch64 that detection must be done by us since `Level` does none).

## 3. CRC-32/BZIP2 (poly 0x04C11DB7, init/xorout 0xFFFFFFFF, refin/refout false; check 0xFC891918)

How much it matters: bz2-ng decompresses at up to ~480 MB/s, so a 0.5 GB/s byte-table CRC (what libbz2 and libbz2-rs-sys use) would roughly halve decode throughput. Slice-by-16 (~3 GB/s) costs ~15%; CLMUL folding (tens of GB/s) is noise.

- **`crc` 3.4.0** (`crc-3.4.0/src/lib.rs:51-66`): implementations `NoTable` (`Table<0>`), `Table<1>` (default, bytewise) and `Table<16>` (slice-by-16, 16×256×4 = 16 KiB table, built at compile time by `const fn`). `crc::Crc::<u32, crc::Table<16>>::new(&crc::CRC_32_BZIP2)` works (`crc-catalog-2.5.0/src/algorithm.rs:2201`). README benchmark (Ryzen 7 3800X): CRC-32 bytewise 0.516 GiB/s, slice-16 3.30 GiB/s. No SIMD. Good portable fallback, matches bz2-ng's own `bzng_crc32_slice16` (`c/lib/crc32.c`).
- **`crc-fast` 1.10.0** (Don MacAskill, `github.com/awesomized/crc-fast-rust`, MIT OR Apache-2.0, 2025-12-31, ~63M downloads, MSRV 1.89, pure Rust with intrinsics, no build script, optional deps only): `CrcAlgorithm::Crc32Bzip2` is supported (`src/lib.rs:291, 845`), plus arbitrary Rocksoft params and a `Digest` with `update`/`finalize` and `new_with_init_state` (needed because bzip2 updates the block CRC across many caller chunks). Runtime-dispatched PCLMULQDQ / AVX-512+VPCLMULQDQ on x86, PMULL / PMULL+EOR3 (sha3) on aarch64, table fallback elsewhere. README numbers for CRC-32/BZIP2 (forward): 1 KiB / 1 MiB = ~20 / ~56 GiB/s Sapphire Rapids, ~14 / ~43 Genoa, ~18 / ~40 Graviton4, ~47 / ~64 GiB/s M4 Max. Forward variants are slower than reflected ones due to the byte-reverse shuffle — the same trick bz2-ng uses (`c/lib/x86/crc32_clmul.h: bzng_rev16`). This is the zero-effort option; the 1 KiB numbers matter because bzip2 CRC calls can be small (per caller chunk / per run).
- **`crc32fast` 1.5.x** is already in seqair's lockfile (via flate2) but computes only the reflected CRC-32/ISO-HDLC; unusable for BZIP2.
- **Hand-written** is feasible on stable: verified on rustc 1.96 that `core::arch::x86_64::_mm_clmulepi64_si128` (`#[target_feature(enable = "pclmulqdq,sse4.1")]`), `_mm512_clmulepi64_epi128` (`vpclmulqdq,avx512f`), `core::arch::aarch64::vmull_p64` (`#[target_feature(enable = "aes")]`), `veor3q_u8` (`sha3`) and `__crc32d` (`crc`) all compile on stable, and `is_aarch64_feature_detected!("pmull" | "crc" | "sha3")` works. bz2-ng's kernels (`x86/crc32_pclmul.c`, `x86/crc32_vpclmul.c`, `arm/crc32_pmull.c`, `arm/crc32_armv8.c`, constants in `crc32.h`) are ~350 lines total and would port almost line-for-line.
- **How bz2-ng uses the ARMv8 CRC32 instructions for a non-reflected CRC** (`c/lib/arm/crc32_armv8.c`): `crc32x/crc32b` compute the reflected CRC with the same polynomial 0x04C11DB7, so it bit-reverses the CRC register on entry and exit (`__rbit(crc)`), and feeds each 8-byte word with the bits of every byte reversed while keeping byte order (`__revll(__rbitll(x))` = rbit whole word then rev bytes). Tail bytes go through `__crc32b(r, rbit(byte) >> 24)`. The PMULL kernel (`arm/crc32_pmull.c`) byte-reverses each 16-byte block so no bit reflection is needed, folds eight accumulators by 1024 bits, and finishes the 128-bit residual and tail with the CRC32-instruction kernel. In Rust: `u32::reverse_bits` → `rbit`, `u64::reverse_bits().swap_bytes()` → `rbit`+`rev`.

Recommendation: start with `crc-fast` (`Digest` with `Crc32Bzip2`), keep `crc` `Table<16>` as a reference/fallback in tests; port bz2-ng's own kernels only if `crc-fast`'s small-buffer overhead shows up in profiles (its generic Rocksoft machinery and dispatch per call vs bz2-ng's direct function pointer).

## 4. Software prefetch on stable Rust

- x86_64: `core::arch::x86_64::_mm_prefetch::<_MM_HINT_T0>(p as *const i8)` — stable, `unsafe` call but no target feature required. `_MM_HINT_ET0` (write intent) also compiles on stable; without `prfchw` enabled it emits plain `prefetcht0` (verified via `--emit asm`), which is what bz2-ng's MSVC path does too.
- aarch64: `core::arch::aarch64::_prefetch` is **unstable** (`stdarch_aarch64_prefetch`, rust-lang/rust#117217 — verified error E0658 on 1.96); `core::intrinsics::prefetch_read_data` is `core_intrinsics` (unstable). Stable alternative, verified to emit `prfm`: `unsafe { core::arch::asm!("prfm pldl1keep, [{0}]", in(reg) ptr, options(nostack, preserves_flags, readonly)) }` (`nomem` would also be defensible since prfm has no architectural memory effect; `pstl1keep` for write intent). Inline asm is opaque to LLVM (no scheduling across it, no folding of the address computation) — acceptable for the 24-chain inverse-BWT walk, but worth checking in the disassembly.

## 5. libsais from Rust

bz2-ng vendors libsais commit `1a696e6` (after 2.10.4) specifically because that commit relicensed libsais to **Apache-2.0 WITH LLVM-exception** (`THIRD_PARTY.md`; `c/third_party/libsais/libsais.h` still says 2.10.4). bz2-ng calls `libsais_ctx(ctx, T, SA, n, fs, freq)` (suffix array, not `libsais_bwt`) with fs ≥ floor(n/2) so libsais never allocates during the recursion, builds the single-thread ctx itself with buckets in the caller's work array, and `#define`s malloc/free for libsais to enforce bzalloc-only allocation (`c/lib/sort_libsais.c`). For seqair (a Rust app, no `bzalloc` contract) those tricks are unnecessary: reusing a context per encoder plus caller-provided SA buffer with fs gives the same no-allocation-per-block behaviour. Note plain `libsais()` allocates an 8 KiB bucket array per call (`libsais_main`, `libsais.c:6928-6941`); `libsais_ctx` does not.

- **`libsais` 0.2.0** (Felix Droop / feldroop, `github.com/feldroop/libsais-rs`, 2025-09-04, MIT OR Apache-2.0 crate licence): safe builder wrapper over `libsais-sys`. Supports caller buffers and context reuse: `SuffixArrayConstruction::for_text(t).in_borrowed_buffer(&mut sa)` (extra space fs = `sa.len() - text.len()`, `suffix_array.rs:689`) `.single_threaded().with_context(&mut Context::new_single_threaded()).run()`; BWT/unBWT builders also take borrowed buffers. `openmp` feature is **on by default** (pulls `openmp-sys`, needs an OpenMP runtime — awkward on macOS); use `default-features = false`. Author warns "not yet battle-tested, there might be bugs".
- **`libsais-sys` 0.2.0**: raw bindgen FFI (`libsais`, `libsais_ctx`, `libsais_bwt`, ... incl. 16-bit and 64-bit variants), builds vendored C with `cc` (adds `-DLIBSAIS_OPENMP` with the feature). Vendored version **2.10.4** (`libsais/VERSION`, CHANGES dated 2025-09-01) whose `LICENSE` is **plain Apache-2.0** (no LLVM exception), even though the crate declares `MIT OR Apache-2.0`. For seqair (MIT/Apache, `deny.toml` allows `Apache-2.0`) plain Apache-2.0 is fine; the LLVM exception only matters for GPLv2-only consumers. If we vendor libsais ourselves at `1a696e6`, cargo-deny's allow list would need `Apache-2.0 WITH LLVM-exception` (or the crate's declared licence expression) added. Symbols are exported globally (`libsais`, `libsais_ctx`...), so two copies in one binary would clash — bz2-ng avoids this with static linkage; a Rust build that vendors its own copy should not also link `libsais-sys`.
- **`libsais-rs` 0.2.2** (henriksson-lab / crates.io owner mahogny, 2026-08-01, Apache-2.0): a pure-Rust "LLM-mediated faithful (hopefully) translation" of libsais 2.10.4; caller supplies `sa` with `sa.len() >= text.len() + fs`. Self-reported single-thread speed 0.82× C (1.18–1.26× slower) with "don't trust these benchmarks"; changelog says "feature complete and seemingly tested" since 2026-05, CI since 2026-08. Interesting as a no-C option, but the sort is the dominant compression cost in bz2-ng, so a 20% slower sorter eats much of the gain.
- `sais-drum` (feldroop) is an unrelated, unoptimised pure-Rust SA-IS; the author points to the libsais bindings instead.

Recommendation: vendor libsais C (the `1a696e6` relicensed commit, like bz2-ng) behind a tiny `cc` build and call `libsais_ctx` with a reused context and fs ≥ n/2, or use `libsais-sys` with `default-features = false` if plain Apache-2.0 and 2.10.4 are acceptable. Either way this is the one C component; everything else in bz2-ng is portable to Rust.

## 6. Other prior art

- **`bzip2-rs` 0.1.2** (Paolo Barbolini, 2021-02-16, MIT/Apache-2.0): 100% safe pure-Rust decoder only; README lists parallel decoding and encoding as "upcoming"; no speed claims; unmaintained since 2021.
- **`lbzip2` (lbzip2-rs)** 0.5.13 (owner Ignalina, Codeberg "znippy", 2026-10-09, MIT OR Apache-2.0 plus bzip2 licence for code "heavily (ai cloned) inspired" by libbz2): decoder only, block-parallel (reader thread scans block magic, rayon workers). Self-reported single-thread decode 112 MB/s vs C libbz2 80 MB/s (1.4×); parallel roughly on par with C lbzip2 (417 vs 388 MB/s on 8 cores; 1941 vs 1924 MB/s on 32 cores). Different design point (parallel, decode-only); bz2-ng is explicitly single-threaded.
- **`bzip2-os` 0.5.0** (2024-06-13): pure-Rust bzip2 encoder/decoder, "late alpha/early beta", uses SA-IS for repetitive data and multithreading; no maturity or speed evidence found.
- **`bzip3`** 0.12.0: bindings to C libbzip3 1.5.3 — a different format (bzip3 itself uses libsais internally), irrelevant for CRAM/bzip2 compatibility.
- No existing Rust crate combines a libsais-based bzip2 encoder, SIMD MTF/RLE kernels and a multi-chain prefetched inverse BWT; a port of bz2-ng would be the first fast single-threaded Rust bzip2 codec.

## Summary of building blocks

| Need | Choice | Status |
|---|---|---|
| Vector kernels | `fearless_simd` 1.1 (already in seqair) + `kernel!` for NEON nibble masks | all bz2-ng ops covered |
| Runtime dispatch | `Level`/`dispatch!` for vector tiers; own `OnceLock` + `is_*_feature_detected!` for CRC (PCLMUL/PMULL/CRC32/SHA3) | aarch64 `Level` does no detection |
| CRC-32/BZIP2 | `crc-fast` (`Crc32Bzip2`), fallback `crc::Table<16>`; or port bz2-ng's ~350 lines | stable intrinsics verified |
| Prefetch | `_mm_prefetch` (x86); `asm!("prfm ...")` (aarch64) | `_prefetch` on aarch64 unstable |
| BWT sorter | vendored libsais (`1a696e6`, Apache-2.0 WITH LLVM-exception) via `cc`, or `libsais-sys` 2.10.4 (plain Apache-2.0, disable `openmp`) | only C dependency |
| Differential oracle | `bzip2-sys` (C libbz2 1.0.8, already via rust-htslib dev-dep) and `libbz2-rs-sys` | available |
